## 5. Описание и результаты работы программ

### 5.1. Клиент-Сервер на FIFO (`fifo_server.py` и `fifo_client.py`)
* Сервер создает именованный канал запросов `/tmp/calc_request.fifo` системным вызовом `os.mkfifo()`.
* Клиент создает собственный именованный канал `/tmp/calc_resp_<client_id>.fifo`.
* Клиент записывает строку вида `<client_id>:<выражение>`.
* Сервер считывает запрос, безопасно парсит и вычисляет AST-дерево выражения, открывает канал клиента на запись и передает результат.

**Лог выполнения:**
```text
[FIFO Сервер] Создан канал запросов: /tmp/calc_request.fifo
[FIFO Сервер] Запрос от клиента [client_1]: '15 * 4 + 10'
[FIFO Сервер] Ответ отправлен в /tmp/calc_resp_client_1.fifo: 70
[Клиент client_1] Получен ответ от сервера: 70
[FIFO Сервер] Запрос от клиента [client_2]: '(100 - 25) / 5'
[FIFO Сервер] Ответ отправлен в /tmp/calc_resp_client_2.fifo: 15.0
[Клиент client_2] Получен ответ от сервера: 15.0
```

---

### 5.2. Клиент-Сервер на Unix Domain Sockets (`uds_server.py` и `uds_client.py`)
* Сервер создает сокет семейства `AF_UNIX` со streaming-протоколом (`SOCK_STREAM`) по пути `/tmp/calc_uds.sock`.
* При поступлении входящего соединения (`accept()`) сервер порождает дочерний процесс через `fork()`.
* Дочерний процесс обслуживает клиента и завершается (`exit(0)`).
* Сервер устанавливает `signal.signal(signal.SIGCHLD, signal.SIG_IGN)`, предотвращая образование процессов-зомби при завершении воркеров.

**Лог выполнения параллельных запросов:**
```text
[UDS Сервер] Прослушивание Unix-сокета: /tmp/calc_uds.sock
[UDS Сервер] Режим: отдельный дочерний процесс (fork) на каждого клиента.
  [Воркер PID 4971] Запрос: '1000 / (4 + 6)' -> Ответ: '100.0'
[UDS Клиент PID 4970] Результат вычисления: 100.0
  [Воркер PID 4972] Запрос: '50 * 5' -> Ответ: '250'
[UDS Клиент PID 4968] Результат вычисления: 250
  [Воркер PID 4973] Запрос: '2 ** 16 - 1' -> Ответ: '65535'
[UDS Клиент PID 4969] Результат вычисления: 65535
```

## 7. Ответы на контрольные вопросы

### 7.1. Почему разделяемая память — самый быстрый и самый опасный механизм IPC?
1. **Почему самый быстрый:**
   * **Отсутствие копирования (Zero-Copy):** При использовании Pipes или Sockets данные копируются минимум дважды: `User Space процесса A -> Буфер ядра (Ring 0) -> User Space процесса B`. При разделяемой памяти ядро один раз маппит одни и те же физические страницы памяти (Page Frames) в виртуальные адресные пространства обоих процессов. После первоначальной настройки процессы обмениваются данными со скоростью оперативной памяти процессора (через кэш L1/L2/L3 и шину памяти) без единого системного вызова и без смены режима процессора.
2. **Почему самый опасный:**
   * **Отсутствие встроенной синхронизации:** Ядро не защищает разделяемую память от одновременной записи. Если два процесса запишут данные одновременно, произойдет порча памяти (Memory Corruption / Data Race). Программист обязан вручную организовывать синхронизацию (именованные POSIX-семафоры, межпроцессные мьютексы `PTHREAD_PROCESS_SHARED`).
   * **Утечки ресурсов операционной системы:** Сегменты разделяемой памяти (POSIX `shm_open`, System V `shmget`) обладают живучестью на уровне ядра (Kernel Persistence). Если процесс аварийно завершится (SIGSEGV, SIGKILL) и не вызовет `shm_unlink()`, сегмент останется в оперативной памяти (в каталоге `/dev/shm`) вплоть до перезагрузки всей ОС.

### 7.2. Что произойдёт при записи в pipe, у которого закрыты все читающие концы?
Если процесс выполняет операцию записи (`write()`) в канал (pipe или FIFO), у которого закрыты все файловые дескрипторы для чтения (нет ни одного читателя):
1. **Ядро Linux генерирует сигнал `SIGPIPE`:**
   Ядро немедленно отправляет вызывающему процессу сигнал `SIGPIPE` («обрыв канала»). По умолчанию стандартным действием (Default Action) для сигнала `SIGPIPE` является **немедленное аварийное завершение процесса** (Abnormal Termination).
2. **Возврат ошибки `EPIPE`:**
   Если процесс перехватывает сигнал `SIGPIPE` (установлен собственный обработчик) или игнорирует его (`signal(SIGPIPE, SIG_IGN)`):
   * Системный вызов `write()` возвращает `-1`;
   * Глобальная переменная `errno` устанавливается в значение `EPIPE` (*Broken pipe*).
3. **Назначение механизма:** Это архитектурное свойство UNIX предотвращает бесконечную генерацию данных программами в пустоту (например, в конвейере `yes | head -n 5`, когда утилита `head` закрывает вход после 5 строк, `yes` получает `SIGPIPE` и завершается, не зацикливая процессор).
