### 5.2. Задача «производитель–потребитель» (Producer-Consumer)

#### Вариант (а): На семафорах (`prod_cons_sem.py`)
* Семафор `empty = Semaphore(5)` — отслеживает количество свободных слотов.
* Семафор `full = Semaphore(0)` — отслеживает количество заполненных слотов с данными.
* Мьютекс `mutex = Lock()` — обеспечивает взаимное исключение при модификации индексов `head`, `tail` и массива.

```python
# Производитель:
empty.acquire()
with mutex:
    buffer[tail] = item
    tail = (tail + 1) % 5
full.release()

# Потребитель:
full.acquire()
with mutex:
    item = buffer[head]
    head = (head + 1) % 5
empty.release()
```
*Результат теста:* 1000 элементов обработаны за 0.0087 с. Число нарушений инвариантов = 0. Утверждения `assert len(consumed) == 1000` и `assert set(consumed) == set(range(1000))` успешно пройдены.

#### Вариант (б): На условной переменной (`prod_cons_cv.py`)
* Условная переменная `cv = threading.Condition(lock)`.
* Производитель ожидает, пока `count >= capacity`.
* Потребитель ожидает, пока `count == 0`.
* Потоки будят друг друга вызовом `cv.notify_all()`.

*Результат теста:* 1000 элементов обработаны за 0.0059 с. Очередь не переполнялась ($0 \le count \le 5$).

### 5.4. Анализ проблемы `if` vs `while` (Mesa-семантика)

В скрипте `spurious_wakeup_demo.py` воспроизведена классическая ситуация:
Два потребителя (C1 и C2) заснули на пустой очереди. Производитель добавляет **1 элемент** и вызывает `cv.notify_all()`.
* **Что происходит при использовании `if len(items) == 0: cv.wait()`:**
  1. Оба потребителя C1 и C2 выводятся ядром из состояния ожидания.
  2. Потребитель C1 первым захватывает мьютекс, забирает единственный элемент `items.pop(0)` и освобождает мьютекс. Очередь снова пуста!
  3. Потребитель C2 захватывает мьютекс следующим. Поскольку в его коде была конструкция `if`, а не цикл, повторная проверка не выполняется! C2 пытается выполнить `items.pop(0)` над пустым списком.
  4. **Происходит аварийное завершение:**
     ```text
     [CRASH в Потребителе 2] Попытка извлечения из пустого списка! Сработало пробуждение по if!
     ```
* **Почему `while` решает проблему:**
  При цикле `while len(items) == 0: cv.wait()`, проснувшийся поток C2 после захвата мьютекса заново оценивает предикат `len(items) == 0`. Видя, что очередь пуста, он безопасно уходит обратно в сон.
  *Это обусловлено **Mesa-семантикой**: вызов `notify()` лишь переводит поток в состояние готовности (Ready), но не гарантирует немедленный захват CPU и неизменность условия в момент захвата мьютекса.*

## 6. Ответы на контрольные вопросы

### 6.1. Чем семафор со значением 1 отличается от мьютекса на практике?
Хотя бинарный семафор (со значением 1) и мьютекс часто взаимозаменяемы для реализации взаимного исключения, между ними есть три ключевых различия:
1. **Концепция владения (Ownership):**
   * **Мьютекс обладает понятием владельца:** Поток, вызвавший `lock.acquire()`, является владельцем мьютекса. Только этот же самый поток имеет право вызвать `lock.release()`. Если другой поток попытается освободить чужой мьютекс, ОС выбросит ошибку (`EPERM` в POSIX) или поведение будет не определено.
   * **У семафора нет владельца:** Семафор — это защищенный счетчик ресурсов. Один поток может вызвать `sem.wait()`, а совершенно другой поток или даже обработчик прерывания (ISR) может вызвать `sem.post()`. Поэтому семафоры используются не только для взаимного исключения, но и для **сигнализации (Signaling)** между потоками.
2. **Протоколы предотвращения инверсии приоритетов:**
   * Мьютексы в ОС поддерживают протоколы **Priority Inheritance** (наследование приоритета) или **Priority Ceiling**. Если высокоприоритетный поток ждет мьютекс, удерживаемый низкоприоритетным потоком, приоритет низкоприоритетного временно повышается.
   * Для семафоров наследование приоритетов невозможно, так как ОС не знает, какой именно поток в будущем вызовет `post()`.
3. **Рекурсивный захват (Reentrancy):**
   * Мьютексы могут быть рекурсивными (`pthread_mutex_recursive` / `threading.RLock`), позволяя одному и тому же потоку захватывать замок несколько раз без дедлока. Семафор при повторном `wait()` уменьшит счетчик до 0 и заблокирует сам себя.

### 6.2. Почему условную переменную нельзя использовать без мьютекса?
Условная переменная (Condition Variable) предназначена для ожидания изменения некоторого **пользовательского предиката состояния** (например, `count == 0` или `buffer is full`). Без мьютекса возникает неустранимое состояние гонки (Race Condition):
1. **Гонка между проверкой условия и сном (Lost Wakeup):**
   Поток-читатель проверяет условие: `if (count == 0)`.
   В этот момент процессор переключается на поток-писатель. Писатель добавляет данные (`count = 1`) и вызывает `cv.signal()`. Поскольку читатель еще не успел уснуть, сигнал `signal()` теряется в пустоте.
   Затем управление возвращается читателю, и он засыпает на `cv.wait()`, ожидая сигнала, который **уже был отправлен**. Читатель зависает навсегда.
2. **Атомарность `wait()`:**
   Операция `cv.wait(mutex)` спроектирована так, чтобы **атомарно** выполнить два действия:
   * Освободить мьютекс;
   * Перевести вызывающий поток в очередь ожидания условной переменной.
   Мьютекс защищает предикат от модификации между моментом проверки и моментом засыпания. При пробуждении поток гарантированно вновь захватывает мьютекс до возврата из `wait()`.
