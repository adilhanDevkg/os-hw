## 5. Выполнение задания и команды

### 5.1. Создание группы и пользователя
```bash
sudo groupadd developers
sudo useradd -m -s /bin/bash -g developers student2
id student2
```
*Вывод команды `id student2`:*
```
uid=1001(student2) gid=1001(developers) groups=1001(developers)
```

### 5.2. Создание каталога `/srv/shared` и разграничение прав
Для каталога требуются права:
* Владелец (`root`): чтение, запись, переход (`rwx` = 7)
* Группа (`developers`): чтение, запись, переход (`rwx` = 7) — для создания и удаления файлов
* Остальные (`others`): чтение и переход (`r-x` = 5) — только чтение

Команды настройки:
```bash
sudo mkdir -p /srv/shared
sudo chown root:developers /srv/shared
sudo chmod 2775 /srv/shared
ls -ld /srv/shared
```
*Вывод `ls -ld /srv/shared`:*
```
drwxrwsr-x 2 root developers 4096 Oct 14 22:33 /srv/shared
```
> **Примечание:** Установка специального бита **SGID (2xxx)** (`chmod 2775`) гарантирует, что все новые файлы и подкаталоги, создаваемые любым участником группы `developers` внутри `/srv/shared`, будут автоматически наследовать группу-владельца `developers`, а не первичную группу создателя.

### 5.3. Создание файла от имени `student2` и попытка удаления

1. Создание файла от имени `student2`:
```bash
sudo su - student2 -c "echo 'Секретный отчет проекта' > /srv/shared/report_student2.txt"
ls -l /srv/shared/report_student2.txt
```
*Вывод:*
```
-rw-r--r-- 1 student2 developers 46 Oct 14 22:34 /srv/shared/report_student2.txt
```

2. Попытка удаления от имени основного пользователя (`student`):
* **Случай А (основной пользователь входит в группу `developers`, права `2775`):**
  Удаление проходит **успешно**.
  ```bash
  rm /srv/shared/report_student2.txt
  # Файл удален без ошибок!
  ```
* **Случай Б (основной пользователь НЕ входит в группу `developers`):**
  ```bash
  rm /srv/shared/report_student2.txt
  # rm: cannot remove '/srv/shared/report_student2.txt': Permission denied
  ```
* **Случай В (на каталог установлен Sticky Bit `1775` / `chmod +t`):**
  ```bash
  sudo chmod 1775 /srv/shared
  # Теперь даже члены группы developers не могут удалить чужой файл:
  rm /srv/shared/report_student2.txt
  # rm: cannot remove '/srv/shared/report_student2.txt': Operation not permitted
  ```

#### Объяснение результата (механизм прав в UNIX/Linux):
В ОС Linux операция удаления файла (`unlink()`) модифицирует **содержимое директории** (каталога), а не сам файл! Каталог в UNIX представляет собой файл со списком пар `(имя_файла, номер_inode)`.
Поэтому:
1. Возможность удалить файл зависит исключительно от бита записи (`w`) на **родительский каталог**, а не от прав на сам удаляемый файл. Если у пользователя есть право `w` на каталог `/srv/shared`, он может удалить из него любую запись.
2. Чтобы предотвратить взаимное удаление чужих файлов пользователями из одной группы, используется **Sticky Bit** (флаг `t`, числовое значение `1000` в маске прав, как в `/tmp`). При установленном sticky bit удалить или переименовать файл может только владелец этого файла или суперпользователь `root`.

## 6. Ответы на теоретические вопросы

### 6.1. Чем `su` отличается от `sudo`?
| Критерий | `su` (Substitute User) | `sudo` (SuperUser DO) |
|---|---|---|
| **Чей пароль вводится** | Пароль **целевого пользователя** (для перехода в root нужно знать пароль root) | Пароль **текущего пользователя** (проверяется членство в группе `sudo`/`wheel`) |
| **Принцип работы** | Полная смена сессии (переключение на другой UID/GID) | Выполнение **одной конкретной команды** с повышенными привилегиями |
| **Аудит и безопасность** | Нет встроенного детального гранулярного аудита | Логирование каждой команды в системный журнал (`/var/log/auth.log`, `journalctl`) |
| **Конфигурация** | Простой бинарник `setuid` | Тонкая настройка прав в файле `/etc/sudoers` (директивы `visudo`, ограничение запуска отдельных утилит) |

### 6.2. Почему в Ubuntu по умолчанию заблокирован вход под root?
1. **Защита от случайных критических ошибок:** Работа под постоянной учетной записью root лишает пользователя барьера перед разрушительными командами (`rm -rf /`, случайное перенаправление в системный диск `/dev/sda`). Использование `sudo` заставляет осознанно повышать привилегии для конкретного действия.
2. **Безопасность при удаленном доступе:** Учетная запись `root` существует на любой UNIX-системе и является первой мишенью для брутфорс-атак по SSH. В Ubuntu в файле `/etc/shadow` пароль root помечен символом `!` (заблокирован), поэтому парольная аутентификация root невозможна.
3. **Персональная ответственность и аудит:** При работе нескольких администраторов через `sudo` всегда видно, кто именно (какой реальный пользователь) выполнил привилегированную команду, в то время как общая сессия `su` стирает след реального автора изменений.

## 7. Настройка `~/.bashrc`

В конец файла `~/.bashrc` добавлены строки:
```bash
# Дополнительные настройки для ПР-1
export OS_LAB_ENV="OperatingSystems_Salymbekov_2026"
alias ll='ls -lah --color=auto'
alias myproc='ps -u $USER -o pid,stat,time,comm'
```

### Проверка в новой сессии терминала:
```bash
bash -i -c 'echo "ENV: $OS_LAB_ENV"; alias ll; alias myproc'
```
*Вывод:*
```
ENV: OperatingSystems_Salymbekov_2026
alias ll='ls -lah --color=auto'
alias myproc='ps -u $USER -o pid,stat,time,comm'
```
Переменная окружения `OS_LAB_ENV` экспортируется дочерним процессам, а псевдонимы (алиасы) позволяют быстро просматривать файлы с подробными атрибутами и процессы текущего пользователя.
