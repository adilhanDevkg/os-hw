## 6. Анализ системных вызовов (strace)

### 6.1. Программа `hello.py`
Код открывает файл в двоичном режиме, считывает его размер и выводит результат:
```python
with open("data/01.log", "rb") as f:
    content = f.read()
    size = len(content)
print(f"Файл: 01.log, Размер: {size} байт")
```

### 6.2. Анализ трассы `trace.txt`
При выполнении команды:
```bash
strace -f -o trace.txt python3 hello.py data/01.log
```

1. **Всего системных вызовов:** от 800 до 1100 (в зависимости от минорной версии Python 3.11/3.12 и дистрибутива).
2. **Системные вызовы, относящиеся непосредственно к файлу `data/01.log`:**
   * `openat(AT_FDCWD, "data/01.log", O_RDONLY|O_CLOEXEC) = 3` — открытие файла в ядре, выделение дескриптора fd=3.
   * `fstat(3, {st_mode=..., st_size=6542, ...}) = 0` — запрос метаданных файла для определения размера буфера.
   * `read(3, "...", 6543) = 6542` — копирование байтов из page cache ядра в буфер процесса.
   * `close(3) = 0` — освобождение файлового дескриптора.
   * Дополнительно: `write(1, "Файл: ...\n", 45)` — вывод на консоль (`stdout`).
   
   **Итого:** Непосредственно для полезной работы нужно всего **4 системных вызова** (`openat`, `fstat`, `read`, `close`) + 1 `write`.

3. **Почему остальные 99% вызовов — накладные расходы интерпретатора:**
   * **Динамический линковщик (`ld.so`):** поиск и маппинг динамических библиотек libc, libm, libz через `openat`, `mmap`, `mprotect`, `close`.
   * **Инициализация адресного пространства:** выделение стека и кучи (`brk`, `mmap` анонимных страниц).
   * **Многопоточность и безопасность:** `arch_prctl`, `set_tid_address`, `set_robust_list`, `prlimit64`.
   * **Инициализация сигнатур среды Python:** перехват сигналов `rt_sigaction` (SIGINT, SIGTERM для обработки исключений Python `KeyboardInterrupt`).
   * **Загрузка базовых модулей и кодировок:** импорт встроенных модулей (`_io`, `sys`, `encodings.utf_8`, `os`) требует множества вызовов `openat`, `fstat`, `stat` для поиска байткода `.pyc` в `sys.path`.

## 7. Сравнение `cat` и `python3 hello.py`

| Параметр | Утилита `cat data/01.log` | Программа `python3 hello.py data/01.log` |
|---|---|---|
| **Язык реализации** | C (скомпилированный ELF бинарник) | Высокоуровневый интерпретируемый Python |
| **Всего системных вызовов** | ~25–35 | ~850–1100 |
| **Время запуска (startup overhead)** | < 1 мс | ~20–40 мс |
| **Используемая память (RSS)** | ~1–2 МБ | ~12–18 МБ |
| **Основной объем вызовов** | Однократный `mmap` libc, `openat`, `fstat`, один большой `read` (128 КБ) и `write` | Инициализация виртуальной машины Python (CPython VM), парсинг байткода, инициализация таблиц типов |

### Вывод из сравнения:
Интерпретатор Python предоставляет колоссальное удобство для программиста, безопасность памяти и богатую стандартную библиотеку, однако платит за это высоким оверхедом при холодном старте. Утилиты уровня `cat`, написанные на C, обращаются к ядру минимально необходимым числом вызовов, выполняя задачу ввода-вывода практически с аппаратной скоростью.

## 8. Ответы на контрольные вопросы

### 8.1. Почему нельзя обратиться к диску напрямую из пользовательской программы?
1. **Безопасность и изоляция (Protection Rings):** Прямой доступ к контроллеру диска (портам ввода-вывода I/O ports или регистрам MMIO) требует привилегированного режима процессора (Ring 0). Если бы любая программа могла напрямую слать команды контроллеру NVMe/SATA, она могла бы перезаписать данные чужих пользователей, системные области или разрушить метаданные файловой системы (суперблок, inode bitmap).
2. **Абстракция и виртуализация:** Пользовательская программа оперирует понятием «файл», а диск оперирует «секторами/LBA-блоками». Ядро берет на себя трансляцию файлов в физические блоки (ext4, btrfs), управление кэшированием (Page Cache), планирование запросов к диску (I/O schedulers) и журналирование.
3. **Конкурентный доступ:** Без централизованного арбитра (ядра) одновременная запись двух программ на один диск привела бы к мгновенному повреждению данных.

### 8.2. Что дороже — вызов функции или системный вызов, и почему?
**Системный вызов несоизмеримо дороже обычного вызова функции** (примерно в 100–1000 раз: вызов функции занимает ~1–2 нс, а syscall — от 100 до 1500+ нс):
1. **Смена кольца защиты (Ring 3 → Ring 0):** Процессор должен переключить режим привилегий с проверкой дескрипторов сегментов и прав доступа (инструкция `syscall` на x86_64).
2. **Переключение стека:** Ядро не доверяет стеку пользователя (он может быть переполнен или поврежден), поэтому процессор аппаратно переключает регистр `RSP` на безопасный стек ядра (kernel stack).
3. **Сохранение и восстановление контекста:** В ядре сохраняются регистры общего назначения пользователя, флаги процессора и адрес возврата (`RIP`).
4. **Валидация аргументов:** Ядро обязано проверить, что переданные указатели находятся в адресном пространстве процесса, не указывают на память ядра и доступны на чтение/запись (`access_ok`).
5. **Меры против уязвимостей спекулятивного выполнения:** Механизмы KPTI (Kernel Page Table Isolation) требуют переключения таблиц страниц памяти (CR3), что приводит к сбросу кэша трансляции адресов (TLB).
